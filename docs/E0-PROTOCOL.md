## 1. Purpose

E0 is a pilot, not evidence. It exists to answer two questions cheaply, before
committing to the full RelayBench grid:

1. **Does the instrumentation work?** Can we capture exploration tokens per leg,
   reliably, from real agent runs?
2. **Is there a signal worth chasing?** Is the C0→C3 difference in exploration
   tokens large enough that the full experiment is worth its cost?

E0 is explicitly **underpowered for publication**. Its result is a go/no-go on
E1, and a magnitude estimate for powering it. It will not appear in the paper as
a finding — only, at most, as a design note.

---

## 2. Research question and hypothesis

Narrowed from RQ2 (RESEARCH.md §1):

> Does a project-owned codebase map plus session handoff reduce the tokens an
> agent spends re-exploring a repository it has worked in before?

**H1.** In legs 2 and 3, agents in C3 spend fewer exploration tokens before
their first edit than agents in C0.

**H0.** No difference in exploration tokens between conditions.

Leg 1 is a control: both conditions start from a cold repository with no
accumulated memory, so H1 predicts **no difference in leg 1**. A difference in
leg 1 indicates a broken harness or a prompt-length confound, not an effect.
This is the pilot's main internal validity check.

---

## 3. Design

**Two conditions, three legs, one repository, n = 5 seeds.**

| Condition | Setup |
|---|---|
| **C0 — no memory** | Cold start every leg. No `.mastishk/`, no notes file, no carryover. The agent gets the repo, the task, and nothing else. |
| **C3 — Mastishk** | `mastishk init` + `scan` before leg 1. Each leg begins with `mastishk session start --agent <id> --task "<leg task>"` and ends with `mastishk session end`. Post-commit hook active. |

Sessions are **context-isolated**: each leg is a fresh agent process with no
conversation history. The only channel between legs is the repository itself
(both conditions) and `.mastishk/` (C3 only).

Total runs: 2 conditions × 3 legs × 5 seeds = **30 sessions**.

Seeds differ only in the agent's sampling seed / temperature draw. Repository
state at the start of each relay is reset to the pinned commit.

### 3.1 Order and independence

Each seed runs a complete relay (legs 1→2→3) in order, because later legs depend
on earlier ones. Seeds are independent: seed *k*'s leg 3 never sees seed *j*'s
work. Condition order is interleaved (C0 seed 1, C3 seed 1, C0 seed 2, …) so that
any drift in the underlying model over the collection window affects both
conditions equally.

## 4. Materials

### 4.1 Repository

**Recommended: `sindresorhus/got` @ `e3924aa`** (already cloned and scanned during
implementation testing).

| Property | Value |
|---|---|
| Language | TypeScript |
| Source files (excl. tests/docs) | 25 |
| Test suite | ava, runs offline |
| Map entries generated by `scan` | 25 (11 with inferred summaries, 12 placeholders) |

Rationale: real third-party code, none of it written by this project's author;
small enough that a 3-leg relay is affordable; has a runnable test suite for
machine-checkable success.

**Known limitation — training-data leakage.** `got` is a popular package and is
almost certainly in the model's training data, which may depress exploration in
*both* arms and compress the effect. For a pilot measuring instrument
feasibility this is acceptable, and it biases against H1 rather than toward it.
E1 must add at least one low-profile or private repository (RESEARCH.md §5).

### 4.2 Legs

Legs must have machine-checkable success and genuine cross-leg dependency. Draft
(to be finalised against the actual codebase before registration is locked):

1. **Establish** — add a documented retry-budget option that caps total retry
   time across redirects. Establishes a constraint: *retry accounting lives in
   `calculate-retry-delay.ts`; no other module may compute delays.*
2. **Repair** — a seeded bug where a redirect path bypasses the leg-1 budget.
   Success requires locating the leg-1 design and fixing within it.
3. **Extend** — surface the remaining budget on the response object, honouring
   the leg-1 constraint.

Leg 2 and leg 3 are where H1 applies: both require knowing what leg 1 decided
and where it lives.

**Success criteria per leg:** the repository's existing test suite passes, plus a
leg-specific test added by the harness (not visible to the agent), plus a static
check that the leg-1 constraint is not violated.

### 4.3 Prompts

Both conditions receive an identical task statement. C3 additionally receives the
standard `AGENTS.md` briefing that `mastishk init` writes; C0 receives no
instruction file. **All prompts are published verbatim with the results.**

Prompt-length asymmetry is a known confound: C3's session-start output is itself
tokens. That is why memory-read tokens are measured and reported separately
(§5.2) and why total tokens is a co-primary outcome.

## 5. Operational definitions

The metric decides the result, so it is pinned here in full.

### 5.1 Primary outcome — exploration tokens

> **Exploration tokens** = the sum of tokens in the *results* of read-only
> repository inspection tool calls issued by the agent in a leg, counted from the
> start of the session until the agent's first successful file mutation.

Precisely:

- **Counted tools:** file reads, directory listings, glob/find, grep/content
  search, and any shell command whose purpose is inspection (`cat`, `ls`, `find`,
  `grep`, `rg`, `head`, `tail`, `tree`, `wc`).
- **Not counted:** the task prompt; the system prompt; the agent's own output
  tokens; test-run output; the memory read (§5.2).
- **Result tokens, not call tokens.** What the agent *receives* is the cost being
  measured; the call itself is negligible and agent-specific.
- **Window:** session start → first successful mutation (write/edit/patch that
  changes a tracked file). Inspection after the first edit is normal
  implementation work, not re-exploration, and is excluded.
- **Tokeniser:** a single fixed tokeniser applied uniformly to both conditions,
  recorded by name and version in the results. Any consistent tokeniser is valid
  since only the between-condition comparison is interpreted.
- **A leg with zero exploration before its first edit records 0**, and is flagged
  for manual inspection — it usually indicates a harness fault.

### 5.2 Co-primary outcome — memory overhead and net tokens

- **Memory-read tokens (C3 only):** tokens in the `mastishk session start`
  output, plus any `inject`, `catchup`, `map` or node-read results.
- **Memory-write tokens (C3 only):** tokens the agent spends composing handoffs
  and node updates.
- **Net token delta** = (C3 exploration + C3 memory overhead) − (C0 exploration).

**A reduction in exploration tokens that is smaller than the memory overhead is
not a win, and will be reported as a null or negative result.** This is the
honest form of RQ2 and the number most likely to be uncomfortable.

### 5.3 Secondary outcomes

Recorded but **not** used to declare success — they exist to catch
mechanism-level surprises and to power E1:

- Leg success (tests pass) and relay completion
- Constraint violations (static check against the leg-1 decision)
- Wall-clock and total tokens per leg
- **Adherence:** did the C3 agent actually call `session start`/`session end`?
  Runs where it did not are reported separately, not silently dropped.
- Map staleness events observed, and whether the agent acted on them

## 6. Registered prediction

Written before any run.

> **Primary:** In legs 2 and 3, C3 exploration tokens will be **lower** than C0
> by a median of **at least 25%**. In leg 1, the two conditions will differ by
> **less than 10%** in either direction.
>
> **Co-primary:** C3 memory overhead will consume **less than half** of the
> exploration-token saving in legs 2–3, leaving a net reduction.
>
> **Confidence:** moderate on the primary, low on the co-primary. The map is the
> mechanism expected to dominate (RESEARCH.md A3), and `fact-scan-map-quality`
> records that only 11 of 25 scanned entries on this repository carry a useful
> summary before any agent refines them — so the leg-2 benefit may be materially
> smaller than the mechanism allows at full map quality.

### 6.1 What would falsify H1

Any of the following is a negative result and will be reported as such:

- Legs 2–3 show **< 10%** median reduction in exploration tokens
- Leg 1 shows a **> 10%** difference in either direction (harness invalid — the
  run is discarded and the harness fixed before any re-run)
- Memory overhead **exceeds** the exploration saving (net loss)
- C3 leg success rate is **lower** than C0

### 6.2 Go / no-go for E1

- **Go:** primary prediction met, or a ≥ 15% reduction with a clean leg-1 control.
- **Investigate, don't scale:** reduction present but swamped by memory overhead —
  the mechanism works and the packaging is wrong; fix before E1.
- **No-go:** no reduction, or leg-1 control fails. Redesign the legs or the
  metric before spending E1's budget.

## 7. Analysis plan

- **n = 5 seeds per condition**, fixed in advance. No optional stopping: data
  collection ends at 30 sessions regardless of what the interim numbers look like.
- Report **median and interquartile range** per condition per leg. With n = 5 the
  distribution shape is unknown and means are fragile.
- Report the **paired per-seed difference** (C3 seed *k* − C0 seed *k*) with a
  bootstrap confidence interval on the median difference.
- **No null-hypothesis significance testing.** n = 5 cannot support it, and a
  p-value here would be theatre. Effect sizes and intervals only.
- Every run's full tool-call trace is retained and published, including failures.
- Runs where the C3 agent skipped the session protocol are reported as a separate
  adherence line, never removed from the denominator.

## 8. Threats specific to E0

| Threat | Handling |
|---|---|
| Training-data leakage on `got` | Acknowledged; biases against H1; E1 adds a low-profile repo |
| Map quality confound | `fact-scan-map-quality`: scan seeds ~44% useful entries here. Leg 1 refines the map naturally; scan-only and refined numbers reported separately |
| Prompt-length asymmetry | Memory tokens measured separately; net delta is co-primary |
| Agent skips the protocol | Adherence measured and reported, not silently excluded |
| Author-designed legs | Legs and success checks published; leg design fixed before any run |
| Small n | Pilot only; explicitly not a publishable finding |
| Author-run experiment | Full harness, prompts, traces and analysis code published |

## 9. Open decisions — need input before this can be locked

These are the items I cannot settle alone. E0 cannot start until they are fixed
and written into this document.

1. **Agent harness.** What actually drives the sessions and emits tool-call
   traces? Options: Claude Code headless (`claude -p` with streamed JSON output),
   the Claude Agent SDK, or a custom API tool loop. This determines the trace
   format and therefore the whole instrumentation layer.
2. **Model and budget.** Which model, pinned to which version, and what is the
   acceptable spend for 30 sessions? This is real money and it caps n.
3. **Repository.** Accept `got @ e3924aa`, or choose something less likely to be
   in training data? A lower-profile repo strengthens E0 at the cost of setup
   time.
4. **Who writes the legs.** Leg design determines the result. Author-designed
   legs are a stated threat; the mitigation is publishing them, but an
   independent pass over the leg definitions would be stronger.
5. **Registration.** Keep this internal, or submit as a registered report to
   EMSE / ICSE-RR before running? The latter gets the design peer-reviewed and
   makes a null result publishable.
